# Release process

## Projects

| Project | What | Library |
|---|---|---|
| Portal Library (`library/`) | All logic and HTML | — |
| Portal - DEV (`shell/`) | Your test firm | Development mode: always the latest pushed code |
| Portal - Template (`template/`) | What lawyers copy | Pinned to a released version, never development mode |

`template/` is generated by the release script from `shell/`. Don't edit it by hand.

## One-time sharing (owner account, in Drive)

1. **Library:** open the Portal Library script in Drive and share it as *Anyone with the link: Viewer*. Firms' copies can't load the library otherwise. Anyone with the link can read the source, so it must never hold secrets.
2. **Template:** share the "Portal - Template" sheet as *Anyone with the link: Viewer*. The copy link is `https://docs.google.com/spreadsheets/d/<template sheet id>/copy`; the release script prints it.

## Releasing

```bash
npm run release -- 0.2.0 "What changed, in one line"
```

The script:
1. refuses unless the git tree is clean, clasp is the owner account and the tests pass;
2. writes the version into `Config.js`, pushes the library and creates library version N;
3. rebuilds `template/` with the library pinned to N and pushes it;
4. adds a CHANGELOG entry.

Then commit and tag:

```bash
git commit -am "Release 0.2.0" && git tag v0.2.0 && git push --follow-tags
```

## Sheet changes between versions

- **Additive changes** (a new tab, column or Settings key): add them to `Config.js`. `Schema.ensure` adds them to existing sheets on its next run. Columns are only ever appended, never renamed or removed: the Claude skill depends on the names.
- **Anything else** (moving data, changing stored state): bump `SCHEMA_VERSION` and add a step to `admin/Migrations.js`. Steps must be safe to run twice.
- Migrations run on **Configurar**, on **Guardar** in setup, and from the 5-minute trigger, so an updated firm upgrades within 5 minutes without doing anything.

## Updating existing firms

When you release, tell each firm (email them). The lawyer runs **Portal → Atualizar portal**, which opens a sidebar with five steps (about 3 minutes):
1. open the script editor;
2. Libraries → Portal → choose the highest version → Save;
3. Deploy → Manage deployments;
4. edit the active deployment → New version → Deploy. The portal address doesn't change.
5. **Verificar** compares the version the sheet runs with the version the live portal serves (`<portal>/exec?portal=version`), and applies any sheet migrations straight away.

**Why it isn't automatic:** the update would need the Apps Script API, and that API is off in the hidden Google Cloud project behind every copy. Not even the owner can switch it on: Google returns `resourcemanager.projects.get` missing (tested 2026-10-30). Automating it would need each firm on a standard Cloud project, which is too technical for the target lawyer.

**Shell changes** (`shell/Code.js` or manifest scopes) don't reach existing firms through the update: it only changes the library version. Keep the shell frozen; a shell change means a guided step with each firm.
